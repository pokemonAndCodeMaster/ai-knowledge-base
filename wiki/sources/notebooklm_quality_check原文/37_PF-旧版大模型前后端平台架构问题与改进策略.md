# PF-旧版大模型前后端平台架构问题与改进策略

> 本卡是大模型质检part 的**专属避坑卡**。
> - 上位枢纽：[[质检一站式平台大模型质检模块整体架构]]
> - 现状来源：[[FastAPI后端API层架构]] / [[Vue3前端层架构]]（反面教材来源）
> - 对标人工质检卡：[[PF-旧版验收代码架构问题与改进策略]]（粒度对标：5 大问题清单 + 规避策略）

---

## 1. 架构问题清单与规避策略

基于 KM 调卷报告②识别的现有大模型前后端平台架构问题，逐条对应新架构规避策略：

| # | 旧版问题 | 影响范围 | 新架构规避策略 |
|---|---------|---------|--------------|
| 1 | 版本配置域 router → repository 直连无分层，职责混杂 | `src/api/routers/version.py`、`src/llm/task_repository.py` | 沿用顶层架构 §4 三层架构（Router → Repository → DB），虽省略 AppService 但两层职责边界清晰：Router 只做 HTTP 层 + Pydantic 校验 + 编排 Repository 调用，Repository 只做 DB 层 SQL 封装。详见 [[大模型质检-后端分层与组件边界设计]]。 |
| 2 | 路由前缀无子part 标识（`/api/tasks` 而非 `/api/llm/tasks`） | `src/api/routers/task.py`、`src/api/routers/version.py` | 统一路由前缀 `/api/llm/`（路径 C 折中），与人工质检结构一致。生产任务 `/api/llm/tasks`，版本配置 `/api/llm/versions`。详见 [[大模型质检-API契约与前端交互设计]]。 |
| 3 | 前端 TaskView / VersionView 单组件过于庞大，职责不单一 | `src/frontend/src/views/TaskView.vue`、`src/frontend/src/views/VersionView.vue` | 前端推翻重来，TaskView 拆 5 组件（TaskListView / TaskCreateDialog / TaskDetailPanel / ChannelStatusGrid / RecycleBinTab），VersionView 拆 3 组件（VersionListView / VersionFormDialog / VersionDetailPanel），单组件 <300 行。详见 [[大模型质检-前端页面与状态设计]]。 |
| 4 | 游标分页仅前进无 prev_cursor，前端无法后退 | `src/llm/task_repository.py`、`src/frontend/src/components/TaskListView.vue` | 游标分页补全 prev_cursor，双向分页（next_cursor 前进 + prev_cursor 后退，通过反向查询实现）。详见 [[大模型质检-Repository与数据库访问设计]] / [[大模型质检-生产任务设计]]。 |
| 5 | t_llm_version_config 表 DDL 不完整（[待人类补充] CHECK 约束） | `scripts/sql/` | 正向化表设计，补全完整 DDL + CHECK 约束（channel 枚举约束 + version 非空约束 + config 非空约束）+ 联合唯一约束（UNIQUE(version, channel) WHERE is_deleted=FALSE）+ 索引设计。详见 [[大模型质检-t_llm_version_config表设计]]。 |
| 6 | 现有前端组件未严格遵循前端开发规范（如可能的 any / axios 直用） | `src/frontend/src/` | 前端推翻重来，严格遵循 [[前端开发规范]]：SFC 顺序 template→script→style；style scoped；禁 any；禁 axios 直用（必须经 `api/*.ts` 间接调用）；禁 v-for 无 key。详见 [[大模型质检-前端页面与状态设计]]。 |
