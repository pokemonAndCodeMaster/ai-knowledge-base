# 质检平台数据结构组织设计

> 当前方案不强制建立集中式 `domain/` 目录，采用“组件内就近定义，出现稳定复用后再上移”。

## 1. 为什么不使用集中式 domain 目录

`domain/` 是领域驱动设计中的常见组织方式，但不是 Python 或 FastAPI 项目的标准结构。原方案把枚举、数据库行、采样配置、预览响应都放入 `domain/models.py`，会混合四种变化速度不同的结构：

- 数据库表字段随 migration 变化；
- 采样/规则输入随算法变化；
- Service 内部结果随用例变化；
- API 请求响应随前端交互变化。

集中放置不等于低耦合。低耦合的关键是一个组件只依赖它真正需要的最小结构，而不是所有组件都 import 同一个大文件。

## 2. 放置规则

| 结构 | 首次放置位置 | 何时上移 |
|---|---|---|
| 采样器私有参数/中间结果 | `acceptance/sampler.py` | 被 Service 和其他规则稳定复用时移到 `acceptance/models.py` |
| 通过/打回判定结果 | `acceptance/pass_rules.py` | 多个 Service 均依赖时上移 |
| 快照数据库行映射 | `manual_qc/repository.py` 附近或 `acceptance/models.py` | Repository 与多个 Service 共同依赖时上移 |
| 人员结构 | `personnel/models.py` | 不跨到 acceptance；需要的少量字段通过查询结果或专用结构传递 |
| HTTP 请求/响应 | `api/schemas/acceptance.py`、`personnel.py` | 不上移到内部业务模型 |

上移门槛：至少两个组件实际使用、字段语义稳定、上移能减少重复而不是扩大依赖。

## 3. 前后端契约

后端 dataclass 不直接给前端使用：

```text
前端 TypeScript
    ↕ JSON / OpenAPI
api/schemas/*.py（Pydantic）
    ↕ Router 显式转换
Service / sampler / pass_rules 的内部 Python 结构
```

这样内部模型可以围绕计算优化，API Schema 可以围绕用户交互和兼容性演进，两者不会因字段偶然相似而被绑死。

## 4. 保留 Enum 的范围

适合 Enum：人员角色、题型、快照结论等封闭业务状态。

不再建立 `SamplerName`、`RuleName` Enum，因为名称已经由 `SAMPLER_REGISTRY`、`RULE_REGISTRY` 维护。注册表是策略发现和校验的唯一事实源。

## 5. 建议目录

```text
src/manual_qc/
├── repository.py
├── delta_client.py
├── acceptance/
│   ├── models.py        # 仅放已形成复用的结构，可初期为空或不存在
│   ├── sampler.py
│   ├── pass_rules.py
│   └── services/
└── personnel/
    ├── models.py
    └── services/

src/api/schemas/
├── acceptance.py
└── personnel.py
```

> 护栏：不要因为一个结构“未来可能复用”就提前上移；先在所属组件内定义，真实重复出现后再重构。
