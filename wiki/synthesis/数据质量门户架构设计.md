## 📌 系统定位与业务模块

### 系统目标

把团队所有数据质量能力集成到统一入口，每个模块一个独立页签，共享公共基础设施（用户体系、导航布局、API 网关、通用组件）。

### 业务模块清单

| 模块 ID | 名称 | 核心能力 | 前端入口 URL |
|---------|------|----------|-------------|
| `auto-qc` | 自动化质检 | 规则引擎、自动检测流水线、任务管理 | `/auto-qc` |
| `manual-qc` | 人工质检 | 人工标注审核界面、工单分配 | `/manual-qc` |
| `llm-qc` | 大模型质检 | LLM 驱动的智能质检、Prompt 配置 | `/llm-qc` |
| `topic-guardian` | 专题质量看护 | 专项质量监控看板、趋势分析 | `/topic-guardian` |
| `knowledge` | 知识管理 | AI 知识管理员、知识卡片、图谱可视化 | `/knowledge` |

## 📐 技术选型（每项都说清楚）

### 一句话速查表

| 技术 | Python 类比 | 作用 | 安装方式 |
|------|------------|------|---------|
| **Node.js 20** | Python 解释器 | 运行前端构建工具的基础环境 | `nvm install 20` |
| **pnpm** | pip / conda | 管理前端依赖包 | `npm install -g pnpm` |

### 技术选型决策记录

**为什么用 Vue 3 而不是 React？**
- 团队已有 Vue 3 初步经验（之前 AI 写的原型）
- Vue 的单文件组件（`.vue`）把 HTML + JS + CSS 放一个文件里，对非前端更直观
- Element Plus（Vue 生态的 UI 库）中文文档最完善，表格/表单组件功能最全

**为什么要 TypeScript？**
- 多人协作的必需品：类型定义 = 活文档，新人看类型就知道数据结构
- IDE 自动补全能力大幅提升，减少查文档时间
- 编译时报错 > 运行时报错，早发现 bug

**为什么用 Pinia 而不是 Vuex？**
- Pinia 是 Vue 3 官方推荐的状态管理，API 更简洁
- 完美支持 TypeScript，类型推导开箱即用
- Vuex 已进入维护模式，不再推荐新项目使用

**为什么用 FastAPI 而不是 Flask？**
- 自带请求参数校验（Pydantic）和 API 文档（Swagger UI）
- 原生异步支持，性能更好
- 类型标注驱动，和前端的 TypeScript 理念一致

### 目录设计原则

**原则一：按角色分层，不按功能分层**

```
✅ 正确：按"你是谁"分目录
  views/auto-qc/      → 自动化质检的所有页面
  api/autoQc.ts        → 自动化质检的所有接口调用
  types/autoQc.ts      → 自动化质检的所有类型

❌ 错误：按"做什么"分目录
  pages/               → 所有页面混在一起
  services/            → 所有接口混在一起
```

**原则二：扁平优先，按需嵌套**

```
初始阶段（代码少时）：
  api/autoQc.ts               ← 一个文件搞定

代码量增长后才拆分：
  api/auto-qc/tasks.ts        ← 拆成多个文件
  api/auto-qc/rules.ts
  api/auto-qc/index.ts        ← 统一导出
```

**原则三：就近原则**

```
只有一个模块用的东西 → 放在那个模块的 views/ 目录下
两个以上模块用的东西 → 提升到 components/ 或 utils/
```

## 🔄 核心数据流：从数据库到页面

> 团队第一阶段 80% 的工作模式。

```
GaussDB 表 → Python 查询 → FastAPI 路由 → JSON 响应 → Axios 请求 → Vue 组件渲染
```

### 端到端数据流详解

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────────┐
│  GaussDB    │     │  Python      │     │  FastAPI     │     │  Vue 前端    │
│  (PostgreSQL)│────▶│  业务逻辑    │────▶│  HTTP 路由   │────▶│  页面组件    │
│             │     │              │     │              │     │              │
│ SELECT ...  │     │ get_tasks()  │     │ GET /api/v1/ │     │ el-table     │
│ FROM tasks  │     │ → [{...}]   │     │ tasks        │     │ 渲染表格     │
└─────────────┘     └──────────────┘     └─────────────┘     └──────────────┘
                                               ↑
                                        JSON 响应格式：
                                    {
                                      "code": 0,
                                      "message": "success",
                                      "data": {
                                        "items": [...],
                                        "total": 100
                                      }
                                    }
```

### 统一 API 响应格式约定

所有后端接口必须返回以下格式，前端拦截器据此统一处理：

```python
# 后端（Python）
{
    "code": 0,           # 0=成功，非0=业务错误
    "message": "success",
    "data": { ... }      # 实际数据
}
```

```typescript
// 前端（TypeScript）对应的类型定义
interface ApiResponse<T> {
  code: number
  message: string
  data: T
}

interface PageResult<T> {
  items: T[]
  total: number
  page: number
  size: number
}
```

### API URL 命名规范

```
格式：/api/v1/{模块}/{资源}

GET    /api/v1/llm-qc/tasks              获取任务列表
GET    /api/v1/llm-qc/tasks/123          获取任务详情
POST   /api/v1/llm-qc/tasks              创建任务
PUT    /api/v1/llm-qc/tasks/123          更新任务
DELETE /api/v1/llm-qc/tasks/123          删除任务
GET    /api/v1/llm-qc/tasks/123/results  获取子资源
POST   /api/v1/llm-qc/tasks/123/run      执行操作
```

## 🧩 新增模块扩展指南

### 完整 Checklist（4 步完成）

假设要新增一个「数据回流」模块：

**Step 1：前端 — 创建页面**

```bash
mkdir -p src/frontend/src/views/data-reflux
# 创建 Dashboard.vue（复制已有模块的页面改改）
```

**Step 2：前端 — 添加路由（在 router/index.ts 加几行）**

```typescript
{
  path: '/data-reflux',
  name: 'data-reflux',
  meta: { title: '数据回流', icon: 'Refresh' },
  children: [
    {
      path: '',
      name: 'data-reflux-dashboard',
      component: () => import('@/views/data-reflux/Dashboard.vue'),
      meta: { title: '回流概览' },
    },
  ],
},
```

侧边菜单会自动读取路由配置并显示新入口，**不需要修改菜单组件**。

**Step 3：前端 — 创建 API 文件和类型**

```bash
# src/frontend/src/api/dataReflux.ts — 接口调用
# src/frontend/src/types/dataReflux.ts — 类型定义
```

**Step 4：后端 — 创建路由和业务逻辑**

```bash
# src/api/routers/data_reflux.py — FastAPI 路由
# src/data_reflux/ — 核心业务逻辑
# 在 src/api/main.py 中 include_router
```

### 扩展决策树

```
拿到一个新需求时，按这个流程判断代码放哪里：

Q1: 这是一个全新的业务模块吗？
  → 是：走上面的 4 步 Checklist
  → 否：继续 Q2

Q2: 这是哪个模块的需求？
  → 找到 views/<模块名>/ 目录

Q3: 是一个新页面吗？
  → 是：在 views/<模块名>/ 下新建 .vue 文件 + 加路由
  → 否：在已有页面中修改

Q4: 需要新的后端接口吗？
  → 是：在 api/<模块名>.ts 中新增函数 + 后端新增路由
  → 否：复用已有接口

Q5: 有跨模块复用的组件或逻辑吗？
  → 是：放到 components/ 或 utils/
  → 否：放在模块自己的 views/ 目录里
```

## ⚖️ 关键设计决策记录（ADR）

### ADR-001：选择 SPA 而非 MPA

**决策**：采用单页面应用（SPA）架构，所有模块在同一个 Vue 应用内，通过路由切换页面。

**备选方案**：多页面应用（MPA），每个模块独立部署。

**决策理由**：
- 团队规模小（≤10人），不需要微前端的独立部署能力
- SPA 页面切换无刷新，用户体验更流畅
- 共享布局、组件、登录状态更简单
- 构建部署只有一个产物，运维复杂度低

**何时需要推翻**：如果团队扩大到 30+ 人、模块发布节奏完全独立时，再考虑微前端。

### ADR-002：扁平目录 vs 模块内嵌套

**决策**：采用扁平目录（api/、types/、stores/ 放在外层），而非每个模块内嵌套完整结构。

**决策理由**：
- 当前每个模块代码量少（< 10 个文件），嵌套过深反而找不到文件
- 按文件类型分目录，IDE 搜索更方便
- 随着代码增长，可以渐进式拆分（先扁平，后嵌套）

**何时需要调整**：当某个模块的 api 文件超过 5 个、types 文件超过 3 个时，将该模块的文件收归到 `views/<模块>/api/`、`views/<模块>/types/` 下。

### ADR-003：侧边菜单读路由配置而非独立维护

**决策**：侧边导航菜单直接读取 Vue Router 的路由配置来渲染，不单独维护菜单数组。

**决策理由**：
- 一处修改（路由配置），两处生效（URL 映射 + 菜单显示）
- 避免"加了路由忘了加菜单"的不一致问题
- 路由的 `meta` 字段存放菜单所需的 title 和 icon

## 🚀 环境搭建步骤

### 前提条件
- Ubuntu 20.04 工作站
- Python 3.10 conda 环境（已有）
- 内网 GaussDB 可访问

### 一键安装脚本

```bash
# ── 1. 安装 Node.js 20 ──
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
nvm install 20
node -v   # 验证输出 v20.x.x

# ── 2. 安装 pnpm ──
npm install -g pnpm
pnpm -v   # 验证输出版本号

# ── 3. 创建前端项目 ──
cd /home/yyh/project/ai-knowledge-base/src
pnpm create vite frontend --template vue-ts

# ── 4. 安装依赖 ──
cd frontend
pnpm add vue-router@4 pinia axios element-plus @element-plus/icons-vue echarts
pnpm add -D @types/node eslint prettier

# ── 5. 启动开发服务器 ──
pnpm dev   # 浏览器打开 http://localhost:5173

# ── 6. 后端（在 conda 环境中） ──
conda activate your_env
pip install fastapi uvicorn python-multipart
cd /home/yyh/project/ai-knowledge-base/src/api
uvicorn main:app --reload --port 8000
# API 文档自动生成在 http://localhost:8000/docs
```

### 日常开发流程

```bash
# 每次开发时，开两个终端：

# 终端 1：前端开发服务器
cd src/frontend && pnpm dev

# 终端 2：后端 API 服务器
cd src/api && uvicorn main:app --reload --port 8000

# 然后在浏览器打开 http://localhost:5173 开始开发
# 修改 .vue 文件后浏览器会自动刷新
```
