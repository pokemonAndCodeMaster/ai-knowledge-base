# 质检一站式平台长期架构

本卡综合 `quality_check_pipeline` NotebookLM source 与当前 wiki 卡片，回答两个问题：质检项目组当前在做什么，以及如何把现有前端架构升级为长期可维护、可扩展的一站式平台架构。

## 当前业务实质

质检项目组正在建设一个面向自动驾驶端到端数据生产的工程平台。它不是单纯的前端后台，也不是单一 LLM 调用工具，而是把数据下载、标签/PKL、视频生成、Prompt 生成、LLM 推理、质检任务管理、版本配置、评测与数据集管理逐步收束到一个可运营平台中。

当前系统主轴：

- `src/llm/`：LLM 数据生产 Pipeline，负责 6 通道任务调度、状态聚合、去重锁、视频生成和推理。
- `src/data_check/`：数据质检能力，承担自动驾驶数据检查。
- `src/api/`：FastAPI 统一 API 门面。
- `src/frontend/`：Vue3 + Element Plus 中后台界面。
- `config/application.yaml`：数据库、OBS、质检、LLM、调度等配置中心。

## 当前架构优点

- 单端口部署简化运维：FastAPI 同时提供 `/api` 和前端静态资源。
- 任务页采用任务组概览 + 组内懒加载，适合大数据量任务运营。
- 任务列表使用游标分页，比传统 OFFSET 更适合高频写入任务表。
- 版本配置已独立成模块，为 model/video/prompt 配置演进提供入口。
- API 层通过 `deps.py` 做依赖注入，减少路由层直接绑定实现。
- Pipeline 采用双层状态：通道状态是事实源，任务状态自动派生。
- 去重锁、Watchdog、holder_id 机制已经具备并发生产的工程意识。

## 当前风险

1. **知识卡片与代码可能脱节**：NotebookLM 导出的 source 已经能说明设计，但必须持续绑定 `related_code` 和 `code_hash`，否则会变成过时文档。
2. **前端状态管理临界点将到来**：当前 Task/Version 两页局部状态足够；一旦 Eval/Dataset 与 Task 联动，需要引入 Pinia 或等价状态层。
3. **API 契约需要更稳定**：前后端依赖 Pydantic Schema 和 TS 类型，但如果没有生成/校验机制，接口演进容易漂移。
4. **端到端验证不足会掩盖真实问题**：单元测试无法证明任务创建、调度、页面展示、回收站、版本配置、Pipeline 状态迁转真的跑通。
5. **模块边界需要防止继续膨胀**：`src/llm/` 已承担下载、生成、推理、调度、去重、Watchdog 等职责，后续要靠模块卡和接口契约控熵。

## 推荐长期分层

后端建议稳定为五层：

1. **API 层**：`src/api/routers/*`，只做请求解析、权限/依赖注入、响应组装。
2. **Application Service 层**：编排用例，例如创建任务、重试任务、重置通道、触发评测。
3. **Domain 层**：任务、通道、版本配置、去重锁、数据集、评测报告的核心规则。
4. **Infrastructure 层**：数据库、OBS、LLM API、Celery-Ray、文件系统等外部适配器。
5. **Scheduler/Worker 层**：执行异步任务、Watchdog、幂等恢复和长任务观测。

前端建议稳定为 feature slice：

```text
src/frontend/src/
├── api/              # 后端 API 封装
├── types/            # 与后端契约对应的 TS 类型
├── stores/           # 跨页面状态，确有需要再引入
├── views/
│   ├── task/
│   ├── version/
│   ├── evaluation/
│   └── dataset/
├── components/       # 跨模块通用组件
└── utils/
```

## 当前仓库第一阶段落地

本仓库已按质检项目组目录语义复刻第一版 `src/` 骨架：

- `src/config/`：配置中心，详见 [[配置管理公共模块]]。
- `src/database/`：PostgreSQL 公共连接池与查询助手，详见 [[PostgreSQL数据库公共模块]]。
- `src/api/`：FastAPI 应用入口、依赖注入和健康检查，详见 [[FastAPI应用入口与依赖注入层]]。
- `src/frontend/`：Vue3 前端工程边界，先保留 `api/components/router/stores/types/utils/views` feature slice 落点。
- `src/llm/`、`src/data_check/`、`src/obs/`、`src/clipinfo/`、`src/pkl_vis/`：按质检项目组业务模块先建立目录边界，后续逐模块还原。

第一阶段的工程判断：先让配置、数据库、API 依赖注入成为稳定公共能力，再让业务模块接入；不要让路由层直接连接数据库，也不要让前端直接绑定数据库表结构。

## 演进路线

### P0：先把现有 Task/Version 做稳

- 保持 `/task` 和 `/version` 的端到端可运行。
- 为任务创建、任务组展开、回收站恢复/永久删除、版本配置 CRUD 建立 smoke/e2e 验证。
- 清理 `vue-tsc` 阻断问题，减少 `any`。
- 将现有 `wiki/quality_portal/` 卡片绑定到真实源码和过期检测。

### P1：补齐评测与数据集骨架

- `/eval` 从占位页演进为评测任务入口：选择任务/模型/数据集，生成评测报告。
- `/dataset` 从占位页演进为数据集浏览、筛选、格式化和导出入口。
- 后端为 evaluation/dataset 建立明确 Schema 和 Application Service，不要把逻辑塞进 router。
- 前端若出现跨页联动，引入 Pinia 管理任务、版本、数据集、评测上下文。

### P2：形成可维护平台能力

- 建立 API 契约生成或校验机制，减少 Pydantic 与 TS 类型漂移。
- 将 Pipeline 状态机、去重锁、Watchdog 指标暴露到前端运营页面。
- 增加调度观测：通道耗时、失败原因分布、重试次数、锁等待情况。
- 知识库对每次关键架构变更做 ingest，形成可追踪 ADR/模块卡/避坑卡。

## 设计原则

- 一站式不等于单体混乱；页面可以统一，模块边界必须清楚。
- 前端优先围绕用户任务流组织，不围绕后端表结构直接堆页面。
- 后端 router 不放业务规则，Pipeline 状态规则不散落在 UI 或 API 层。
- 所有状态迁转必须可解释、可重放、可观测。
- 新功能必须带端到端验证路径和知识库更新判断。
