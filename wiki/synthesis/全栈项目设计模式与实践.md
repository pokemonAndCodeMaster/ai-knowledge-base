## 1. 经典分层架构

### 1.1 三层架构（我们的选择）

```
┌─────────────────────────────────────────────┐
│  表现层 (Presentation Layer)                 │
│  前端 Vue 应用：页面渲染、用户交互、数据展示    │
├─────────────────────────────────────────────┤
│  业务逻辑层 (Business Logic Layer)           │
│  FastAPI 路由 + Python 业务模块               │
│  数据校验、权限检查、业务规则执行               │
├─────────────────────────────────────────────┤
│  数据访问层 (Data Access Layer)              │
│  pgconnector + psycopg2                      │
│  SQL 查询、事务管理、连接池                    │
└─────────────────────────────────────────────┘
```

**为什么选三层架构？**
- 最简洁、最成熟、最容易理解的架构模式
- 团队规模小（≤10人），更复杂的架构反而增加心智负担
- 大部分功能是 CRUD（增删改查），三层架构完美匹配

### 1.2 每层的职责边界

```python
# ═══════════════════════════════════════
# 表现层（前端）的职责：
# ═══════════════════════════════════════
# ✅ 做：
#   - 页面渲染和用户交互
#   - 表单校验（基本格式校验：非空、邮箱格式等）
#   - 数据展示格式转换（日期格式化、状态标签等）
#   - 调用后端 API
# ❌ 不做：
#   - 业务逻辑判断（如"只有管理员能删除任务"）
#   - 直接操作数据库
#   - 数据安全性校验

# ═══════════════════════════════════════
# 业务逻辑层（FastAPI + Python）的职责：
# ═══════════════════════════════════════
# ✅ 做：
#   - 业务规则执行（权限检查、状态流转校验）
#   - 数据校验（业务层面：如"任务名不能重复"）
#   - 调用数据访问层获取/修改数据
#   - 组装返回给前端的数据
# ❌ 不做：
#   - 直接拼 SQL（应封装在数据访问层）
#   - 关心前端怎么展示

# ═══════════════════════════════════════
# 数据访问层（pgconnector）的职责：
# ═══════════════════════════════════════
# ✅ 做：
#   - SQL 查询/增删改
#   - 连接管理和连接池
#   - 事务管理
# ❌ 不做：
#   - 业务规则判断
#   - 数据格式化
```

## 2. 前端核心设计模式

### 2.1 容器-展示组件模式（Container-Presentational）

```
核心思想：将组件分为两类
  - 容器组件（Smart）：负责数据获取和业务逻辑
  - 展示组件（Dumb）：只负责渲染 UI，不关心数据从哪来
```

```vue
<!-- 容器组件：TaskListPage.vue（放在 views/ 中） -->
<template>
  <TaskTable
    :tasks="tasks"
    :loading="loading"
    @delete="handleDelete"
    @edit="handleEdit"
  />
</template>

<script setup>
// 这里处理所有数据逻辑
const tasks = ref([])
const loading = ref(false)

async function handleDelete(id) {
  await deleteTask(id)
  loadData()
}
</script>

<!-- 展示组件：TaskTable.vue（放在 components/ 中） -->
<template>
  <el-table :data="tasks" v-loading="loading">
    <!-- 纯 UI 渲染 -->
  </el-table>
</template>

<script setup>
// 只接收数据和发送事件，不做任何业务逻辑
defineProps<{ tasks: Task[]; loading: boolean }>()
defineEmits<{ delete: [id: number]; edit: [task: Task] }>()
</script>
```

**好处**：展示组件可以在多个页面复用。比如 TaskTable 可以同时在自动化质检和大模型质检中使用，只要传入不同的数据。

### 2.2 数据获取模式

```
模式一：页面 onMounted 获取（最简单，大部分场景用这个）
  ─── 适用于：打开页面就需要的数据

模式二：用户操作触发获取
  ─── 适用于：搜索、筛选、翻页

模式三：Store 缓存获取
  ─── 适用于：多个页面都需要的数据（如用户信息、字典数据）

模式四：实时更新获取
  ─── 适用于：需要自动刷新的数据（如任务状态监控）
  ─── 用 setInterval 定时轮询或 WebSocket
```

### 2.3 表单处理模式

```vue
<!-- 标准表单处理模式 -->
<script setup>
// 1. 表单数据初始化
const defaultForm = { name: '', model: '', status: 'pending' }
const form = ref({ ...defaultForm })

// 2. 新建 vs 编辑
const isEdit = ref(false)
function openCreate() {
  isEdit.value = false
  form.value = { ...defaultForm }  // 重置为默认值
  dialogVisible.value = true
}
function openEdit(task: Task) {
  isEdit.value = true
  form.value = { ...task }         // 用已有数据填充
  dialogVisible.value = true
}

// 3. 提交
async function submit() {
  const valid = await formRef.value.validate()
  if (!valid) return
  
  if (isEdit.value) {
    await updateTask(form.value.id, form.value)
  } else {
    await createTask(form.value)
  }
  
  ElMessage.success(isEdit.value ? '更新成功' : '创建成功')
  dialogVisible.value = false
  loadData()  // 刷新列表
}
</script>
```

### 3.1 FastAPI Router 组织模式

```python
app.include_router(manual_qc.router)

from fastapi import APIRouter, Depends, Query

router = APIRouter(
    prefix="/api/v1/llm-qc",     # 统一前缀
    tags=["大模型质检"],            # Swagger 分组
)

@router.get("/tasks")
async def list_tasks(
    page: int = Query(1, ge=1),
    size: int = Query(20, ge=1, le=100),
    status: str | None = Query(None),
):
    # 调用业务逻辑层
    from llm_qc.service import get_tasks
    return {"code": 0, "data": get_tasks(page, size, status)}
```

## 5. 组级别团队的架构原则

### 5.1 YAGNI — 不要做不需要的东西

```
YAGNI = "You Aren't Gonna Need It"（你不会需要它的）

❌ 过度设计的例子：
  - 团队 5 人，搞微服务架构（K8s + Service Mesh）
  - 数据量不大，上 Redis 缓存 + ElasticSearch 全文搜索
  - 只有 5 个模块，做插件化的模块注册系统
  - 没有国际化需求，做 i18n 多语言支持

✅ 正确的做法：
  - 用最简单的方案解决当前问题
  - 在需要时再引入复杂度
  - 代码结构预留扩展空间（目录约定），但不提前写扩展代码
```

### 5.2 渐进式复杂化

```
阶段一：所有代码在一个文件里
  → 当文件超过 200 行时 ——

阶段二：拆分成多个文件
  → 当类似的模式出现 3 次以上时 ——

阶段三：提取成通用模块
  → 当模块有外部使用者时 ——

阶段四：发布成独立包

每次增加复杂度都应该有充分的理由，而不是"以后可能会用到"。
```

### 5.3 保持简洁的具体指南

```
1. 依赖数量控制
   → 每引入一个新依赖，问自己："能不能用已有的东西实现？"
   → package.json 的 dependencies 控制在 15 个以内

2. 抽象层级控制
   → 最多 3 层调用深度：组件 → API → 后端
   → 不要为了"解耦"而引入中间层

3. 配置文件控制
   → 能用约定解决的不写配置
   → 配置文件数量控制在 5 个以内

4. 通用组件控制
   → 被 3 个以上地方使用才提取为通用组件
   → 通用组件不超过 20 个（超过就说明过度封装了）

5. 代码量的警戒线
   → 单文件 > 300 行：考虑拆分
   → 单目录 > 20 个文件：考虑子目录分组
   → 总代码量 > 5 万行：考虑是否有不必要的复杂度
```

### 5.4 技术债管理

```
技术债是不可避免的，关键是如何管理：

1. 记录债务：发现技术债时在代码中写 // TODO: 描述问题和建议方案
2. 定期还债：每个迭代预留 10-20% 时间处理技术债
3. 分级处理：
   - 🔴 阻塞级：影响新功能开发 → 立即处理
   - 🟡 体验级：不影响功能但影响开发效率 → 下个迭代处理
   - 🟢 美化级：代码不够优雅但能正常工作 → 有空再改
```

## 6. 前后端统一的数据流模式

### 6.1 标准 CRUD 数据流

```
创建（Create）：
  前端表单 → POST /api/v1/tasks → 校验 → INSERT → 返回新记录 → 刷新列表

查询（Read）：
  页面加载 → GET /api/v1/tasks?page=1 → SELECT → 返回分页数据 → 渲染表格

更新（Update）：
  编辑表单 → PUT /api/v1/tasks/123 → 校验 → UPDATE → 返回更新记录 → 刷新列表

删除（Delete）：
  确认弹窗 → DELETE /api/v1/tasks/123 → 权限检查 → DELETE → 刷新列表
```

### 6.2 状态流转数据流

```
我们的业务特点：很多操作涉及状态流转（pending → running → completed/failed）。

前端流程：
  1. 用户点击"开始执行"按钮
  2. 前端调用 POST /api/v1/tasks/123/run
  3. 后端校验状态流转是否合法
  4. 合法则更新数据库状态
  5. 返回更新后的任务
  6. 前端根据新状态更新 UI（如按钮变灰、标签变色）

后端校验（状态机）：
  pending → running    ✅（开始执行）
  running → completed  ✅（执行成功）
  running → failed     ✅（执行失败）
  failed  → pending    ✅（重试）
  completed → pending  ❌（不能重新开始已完成的任务）
```

## 7. 项目目录结构对比

### 7.1 不同规模团队的推荐结构

```
── 2-5 人小团队（我们目前）──

src/frontend/src/
├── views/          按模块分子目录
├── components/     通用组件
├── api/            按模块分文件
├── types/          按模块分文件
├── router/         单文件路由配置
└── styles/         全局样式

特点：扁平、直观、一眼看清全貌


── 10-20 人中团队 ──

src/frontend/src/
├── modules/            模块化组织
│   ├── llm-qc/
│   │   ├── views/
│   │   ├── components/
│   │   ├── api/
│   │   └── types/
│   └── auto-qc/
│       └── ...
├── shared/             公共能力
│   ├── components/
│   ├── composables/
│   └── utils/
└── ...

特点：模块隔离清晰，但目录深度增加


── 30+ 人大团队 ──

考虑微前端 (Module Federation / qiankun)
每个模块独立仓库、独立构建、独立部署

特点：完全解耦，但运维复杂度大增
```
