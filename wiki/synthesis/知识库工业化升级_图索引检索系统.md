# 知识库工业化升级：图索引检索系统设计与实现

> 本卡片是完整的技术总纲，可独立复现整个系统。面向新加入的人类或 AI 阅读。

## 🎯 升级目标

**解决的核心问题**：给定一个具体任务，把知识库中**所有相关知识点一网打尽**（领域知识、算法、具体代码、开发规范、历史坑点），并且控制 token 用量。

**升级前的缺陷**：
- Agent 读 `index.md` → 逐文件跟 `[[双链]]` 串行遍历，最坏情况读 10-15 个完整文件
- 无反向关联：pitfall/norm 的 `affects_path` 字段无法被 query 反向利用
- Token 无节制：所有卡片全文读取，~50K token/次 query

**升级后的效果**（55 张卡片实测）：
- 一次 query "设计多 Agent 协作系统" → 21 张相关卡片，仅需全文读 3 张 + 读摘要 3 张
- 估算 token 从 ~50K 降至 ~13K，节省 **75%**

## 🏗️ 系统架构

```
触发层（LLM Agent）
  │  用户给定任务
  ▼
脚本层（Python，确定性计算）
  ├── compile_graph.py  ← 离线编译：Markdown → 图索引 JSON
  ├── query_graph.py    ← 在线查询：任务描述 → 分级卡片清单
  └── check_staleness.py← 周期检测：代码变更 / 孤岛 / 断链
  │
  ▼
产物层（.wiki_graph.json）
  ├── nodes{}: slug → {title, domain, type, tags, trigger_keywords,
  │                    affects_path, related_code, summary,
  │                    outlinks[], inlinks[]}
  └── stats{}: total_cards, total_links, orphan_cards, broken_links
```

## 📐 核心设计决策

### 决策 1：为什么不用向量数据库

| 对比维度 | 向量数据库（Milvus/pgvector） | 本方案（图索引 + 关键词） |
|----------|-------------------------------|--------------------------|
| 当前规模（55卡片） | 过度设计 | 毫秒级，零部署成本 |
| 中文匹配精度 | 需要 Embedding 模型 | n-gram 子串匹配，够用 |
| 图遍历能力 | 需要额外 PPR 实现 | 原生 BFS，无依赖 |
| 升级路径 | 可在 >200 卡片时引入 | 脚本接口稳定，可无缝替换 |

**结论**：55 卡片阶段用纯 Python + 图遍历，等规模 >200 卡片再引入向量检索做 Seed 发现。

### 决策 2：为什么编译产物纳入 git

`.wiki_graph.json` 是从 `wiki/*.md` 派生的确定性产物。纳入 git 的原因：
- 换机器/换 Agent 实例无需重跑编译
- CI/CD 可直接使用（如未来的 eval 脚本）
- 体积小（55 卡片 ~80KB），不影响 repo 大小

### 决策 3：零外部依赖

pip 在某些受控环境中不可用。用纯正则替代 PyYAML 解析 frontmatter，用 n-gram 替代 jieba 做中文分词。未来可选安装 jieba 提升精度，脚本兼容。

### 决策 4：LLM 与脚本分工

| 操作 | 由谁执行 | 理由 |
|------|---------|------|
| 解析 frontmatter | 脚本 | 确定性，速度快 |
| 提取 `[[双链]]` | 脚本 | 正则即可，零误差 |
| BFS 图遍历 | 脚本 | 算法确定，LLM 会出错 |
| 读取优先级排序 | 脚本 | 规则明确，无需推理 |
| 内容语义理解 | LLM | 只有 LLM 能做 |
| 卡片编纂和摘要 | LLM | 需要写作能力 |
| 矛盾/冗余检测 | LLM | 需要语义比较 |

## 🔁 三阶段检索范式（核心算法）

见 [[Seed-Expand-Classify 检索范式]] 卡片获取完整算法细节。

简述：
1. **Seed 发现**：多维加权匹配（trigger_keywords 权重最高 +3.0，title 子串 +2.5，tag 命中 +1.0，domain 匹配 +1.5，路径匹配 +2.5），取 top-5 种子
2. **图扩展**：从种子出发，BFS 双向（outlinks + inlinks）扩展 2 跳
3. **分类交付**：按 type 分桶，按优先级排序（full_read / summary_only / title_only）

## 🔄 更新机制

### 日常增量更新（低频）
```
[ingest] 流程结束 → python scripts/compile_graph.py → 重编译
```

### 代码变更驱动更新（按需）
```
修改代码文件 → python scripts/check_staleness.py --code-only
  → 报告 stale 卡片 → Agent 读 git diff → 更新卡片内容 + code_hash → 重编译
```

### 定期大扫除（周期性）
```
[health] 工作流：
  compile → check_staleness → 读孤岛/断链 → LLM 分析冗余矛盾 → HEALTH_REPORT.md
```

## 📊 设计参考

本方案的核心思路借鉴自两个开源项目的深度分析（见 [[gbrain_yuxi_深度技术分析]]）：
- **gbrain**：Post-Fusion Boost 的多层加权思路（对应本方案的 Seed 多维权重）
- **Yuxi**：`find_kb_document + open_kb_document` 的分级读取工具链（对应本方案的 full_read / summary_only / title_only 三级优先级）
- **共同启示**：图遍历（BFS/PPR）的召回率远优于单纯向量检索，尤其对 pitfall/norm 等语义不相似但逻辑强关联的知识
