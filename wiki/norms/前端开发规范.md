# 📏 前端开发规范

> **强制约束**：本规范中标注为「🔴 强制」的规则，违反时 Code Review 不予通过。标注为「🟡 推荐」的规则，违反时需要在 PR 中说明理由。
> **适用范围**：`src/frontend/` 下的所有代码。
> **关联**：[[数据质量门户架构设计]] | [[前端从零到精通学习指南]]

## 1. 命名规范

### 1.1 文件命名

| 类别 | 规范 | 正确 ✅ | 错误 ❌ | 级别 |
|------|------|---------|---------|------|
| Vue 组件文件 | PascalCase（每个单词首字母大写） | `TaskList.vue` | `task-list.vue`, `taskList.vue` | 🔴 强制 |
| TypeScript 文件 | camelCase（小驼峰） | `autoQc.ts` | `auto-qc.ts`, `AutoQc.ts` | 🔴 强制 |
| API 文件 | camelCase + 模块名 | `autoQc.ts` | `api.ts`, `autoQcApi.ts` | 🔴 强制 |
| 类型定义文件 | camelCase + 模块名 | `autoQc.ts` | `types.ts`, `AutoQcType.ts` | 🔴 强制 |
| 样式文件 | kebab-case（短横线） | `global.css` | `Global.css` | 🟡 推荐 |
| 目录名 | kebab-case | `auto-qc/` | `autoQc/`, `AutoQc/` | 🔴 强制 |

> **为什么 Vue 组件用 PascalCase？**
> 因为在模板中使用组件时写 `<TaskList />`，PascalCase 能一眼区分"自己写的组件"和"HTML 原生标签"（如 `<div>`、`<span>`）。

### 1.2 代码命名

| 类别 | 规范 | 正确 ✅ | 错误 ❌ | 级别 |
|------|------|---------|---------|------|
| 变量名 | camelCase | `taskList` | `task_list`, `TaskList` | 🔴 强制 |
| 函数名 | camelCase，动词开头 | `loadTasks()` | `tasks()`, `TaskLoad()` | 🔴 强制 |
| 常量 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` | `maxPageSize` | 🟡 推荐 |
| 接口/类型名 | PascalCase | `LlmQcTask` | `llmQcTask`, `llm_qc_task` | 🔴 强制 |
| CSS 类名 | kebab-case | `task-card` | `taskCard`, `TaskCard` | 🔴 强制 |
| 路由 name | kebab-case，模块名前缀 | `llm-qc-dashboard` | `dashboard`, `LlmQcDashboard` | 🔴 强制 |
| 自定义事件 | kebab-case | `@task-updated` | `@taskUpdated` | 🔴 强制 |
| Store 名 | camelCase + `use` 前缀 | `useUserStore` | `userStore`, `UserStore` | 🔴 强制 |

### 1.3 API 函数命名规范

```typescript
// 函数命名规范：动词 + 名词
export function getTaskList(...)   // 查询列表
export function getTaskDetail(...) // 查询详情
export function createTask(...)    // 创建
export function updateTask(...)    // 更新
export function deleteTask(...)    // 删除
export function runTask(...)       // 执行操作

// ❌ 不好的命名
export function tasks(...)         // 缺少动词
export function fetchData(...)     // 太笼统
export function doSomething(...)   // 毫无意义
```

## 2. 文件组织规范

### 2.1 新功能放哪里？（决策流程图）

```
拿到新需求 → 判断放哪里：

├── 这是一个新的页面？
│   └── 放在 views/<模块名>/ 下，文件名用 PascalCase
│       例：views/llm-qc/TaskDetail.vue
│
├── 这是页面中可复用的小组件？
│   ├── 只有本模块用？→ 放在 views/<模块名>/ 同目录下
│   │   例：views/llm-qc/TaskStatusTag.vue
│   │
│   └── 多个模块用？→ 提升到 components/
│       例：components/StatusTag.vue
│
├── 需要调用后端新接口？
│   └── 在 api/<模块名>.ts 中新增函数
│       例：api/llmQc.ts 中新增 getTaskResults()
│
├── 需要定义新的数据类型？
│   └── 在 types/<模块名>.ts 中新增 interface
│       例：types/llmQc.ts 中新增 TaskResult 接口
│
├── 需要跨页面共享数据？
│   └── 在 stores/ 中创建或修改 store
│       例：stores/llmQc.ts
│
└── 需要一个通用工具函数（日期格式化、数据转换等）？
    └── 放在 utils/ 目录下
        例：utils/format.ts
```

### 2.2 通用组件命名前缀

```
App 前缀 → 应用级通用组件（全站使用）
  components/AppTable.vue     封装 el-table
  components/AppDialog.vue    封装 el-dialog

无前缀 → 业务通用组件（多个模块使用）
  components/StatusTag.vue    状态标签
  components/SearchForm.vue   搜索表单
  components/PageHeader.vue   页面标题栏
```

### 2.3 文件大小限制

| 指标 | 阈值 | 处理方式 | 级别 |
|------|------|---------|------|
| 单个 `.vue` 文件行数 | > 300 行 | 拆分组件或提取逻辑到 composable | 🟡 推荐 |
| 单个 `.ts` 文件行数 | > 200 行 | 拆分为多个文件 | 🟡 推荐 |
| 单个 API 文件函数数量 | > 15 个 | 拆分为子目录 | 🟡 推荐 |
| views/ 下某模块文件数 | > 10 个 | 考虑用子目录分组 | 🟡 推荐 |

## 3. Vue 组件编写规范

### 3.1 单文件组件结构顺序 🔴 强制

```vue
<!-- 顺序固定为：template → script → style -->

<!-- 1. 模板 — 放最前面（最先关心页面长什么样） -->
<template>
  <div class="task-card">
    ...
  </div>
</template>

<!-- 2. 脚本 — 放中间 -->
<script setup lang="ts">
// 导入顺序：
// ① Vue 生态（vue、vue-router、pinia）
// ② 第三方库（element-plus、echarts）
// ③ 项目内文件（@/api/、@/types/、同目录文件）

// 内部结构顺序：
// ① Props 和 Emits
// ② 响应式数据（ref、reactive）
// ③ 计算属性（computed）
// ④ 方法（function）
// ⑤ 生命周期（onMounted 等）
</script>

<!-- 3. 样式 — 放最后，必须加 scoped -->
<style scoped>
.task-card {
  ...
}
</style>
```

### 3.2 script setup 内部结构模板 🔴 强制

```vue
<script setup lang="ts">
// ═══════════════════════════════════════
// ① 导入
// ═══════════════════════════════════════
import { ref, computed, onMounted } from 'vue'
import { useRouter } from 'vue-router'
import { ElMessage } from 'element-plus'

import { getTaskList, deleteTask } from '@/api/llmQc'
import type { LlmQcTask } from '@/types/llmQc'

// ═══════════════════════════════════════
// ② Props 和 Emits（如果有的话）
// ═══════════════════════════════════════
const props = defineProps<{
  taskId: number
}>()

const emit = defineEmits<{
  'task-updated': [task: LlmQcTask]
}>()

// ═══════════════════════════════════════
// ③ 响应式数据
// ═══════════════════════════════════════
const tasks = ref<LlmQcTask[]>([])
const loading = ref(false)
const page = ref(1)

// ═══════════════════════════════════════
// ④ 计算属性
// ═══════════════════════════════════════
const pendingCount = computed(() =>
  tasks.value.filter(t => t.status === 'pending').length
)

// ═══════════════════════════════════════
// ⑤ 方法
// ═══════════════════════════════════════
async function loadData() {
  loading.value = true
  try {
    const result = await getTaskList({ page: page.value, size: 20 })
    tasks.value = result.items
  } finally {
    loading.value = false
  }
}

// ═══════════════════════════════════════
// ⑥ 生命周期
// ═══════════════════════════════════════
onMounted(() => {
  loadData()
})
</script>
```

### 3.3 模板中的禁止事项 🔴 强制

```vue
<!-- ❌ 禁止在模板中写复杂表达式 -->
<span>{{ tasks.filter(t => t.status === 'done').length }}</span>

<!-- ✅ 应提取为计算属性 -->
<span>{{ doneCount }}</span>
<!-- script 中：const doneCount = computed(() => tasks.value.filter(...).length) -->


<!-- ❌ 禁止在 v-for 中不使用 :key -->
<div v-for="task in tasks">...</div>

<!-- ✅ 必须提供唯一 key -->
<div v-for="task in tasks" :key="task.id">...</div>


<!-- ❌ 禁止直接操作 DOM -->
<script setup>
document.getElementById('xxx').style.color = 'red'  // 不要这样做！
</script>

<!-- ✅ 用 Vue 的响应式方式控制样式 -->
<div :style="{ color: isError ? 'red' : 'inherit' }">...</div>
```

## 4. 样式规范

### 4.1 必须使用 scoped 🔴 强制

```vue
<!-- ✅ 正确 -->
<style scoped>
.task-card { ... }
</style>

<!-- ❌ 错误：不加 scoped 会污染全局样式 -->
<style>
.task-card { ... }  /* 其他组件也叫 .task-card 就被你影响了 */
</style>
```

> **原理**：`scoped` 会让 Vue 自动给这个组件的 HTML 加上一个唯一属性（如 `data-v-7a7a37b1`），CSS 选择器也会被编译为 `.task-card[data-v-7a7a37b1]`，确保样式只作用于当前组件。

### 4.2 使用 CSS 变量 🔴 强制

```css
/* ✅ 正确：使用预定义的 CSS 变量 */
.card {
  color: var(--color-text-primary);
  padding: var(--spacing-md);
  border-radius: var(--radius-md);
  box-shadow: var(--shadow-sm);
}

/* ❌ 错误：硬编码颜色值和数字 */
.card {
  color: #333;
  padding: 16px;
  border-radius: 8px;
  box-shadow: 0 1px 2px rgba(0,0,0,0.1);
}
```

> **为什么？** 改主题色时只需改 `styles/variables.css` 一处，而不是全局搜索替换。

### 4.3 布局规范 🟡 推荐

```css
/* ✅ 推荐使用 Flexbox 和 Grid */
.header {
  display: flex;
  justify-content: space-between;
  align-items: center;
  gap: var(--spacing-md);
}

/* ❌ 不推荐使用 float（上古时代的布局方式） */
.header {
  overflow: hidden;
}
.header .left {
  float: left;
}
```

### 4.4 禁止 !important 🔴 强制

```css
/* ❌ 禁止（除非覆盖第三方组件库样式，且必须注释说明原因） */
.button {
  color: red !important;
}

/* ✅ 如果确实需要覆盖 Element Plus 样式，使用 :deep() */
:deep(.el-button) {
  border-radius: var(--radius-md);
}
```

## 5. TypeScript 规范

### 5.1 禁止 any 🔴 强制

```typescript
// ❌ 禁止
function processData(data: any) { ... }

// ✅ 使用具体类型
function processData(data: LlmQcTask) { ... }

// ✅ 如果确实不确定类型，用 unknown（需要类型守卫后才能使用）
function processUnknown(data: unknown) {
  if (typeof data === 'string') {
    // 这里 data 的类型自动推导为 string
    console.log(data.toUpperCase())
  }
}
```

### 5.2 API 返回值必须定义类型 🔴 强制

```typescript
// ❌ 错误：没有类型定义，调用者不知道返回什么
export function getTaskList(params: any) {
  return request.get('/api/v1/llm-qc/tasks', { params })
}

// ✅ 正确：明确定义参数和返回类型
export function getTaskList(params: { page: number; size: number; status?: string }) {
  return request.get<any, PageResult<LlmQcTask>>('/api/v1/llm-qc/tasks', { params })
}
```

### 5.3 用 interface 而非 type（偏好） 🟡 推荐

```typescript
// ✅ 推荐用 interface（可以被扩展，错误信息更清晰）
interface LlmQcTask {
  id: number
  title: string
}

// 🟡 type 也可以（当需要联合类型、元组等高级功能时用）
type TaskStatus = 'pending' | 'running' | 'completed' | 'failed'
```

## 6. API 调用规范

### 6.1 统一通过 api/ 层调用 🔴 强制

```typescript
// ❌ 禁止在组件中直接使用 axios
import axios from 'axios'
const res = await axios.get('/api/v1/tasks')

// ✅ 必须通过 api/ 层间接调用
import { getTaskList } from '@/api/llmQc'
const result = await getTaskList({ page: 1, size: 20 })
```

> **为什么？** 接口 URL 变了，只需要改 `api/llmQc.ts` 一处，而不是全局搜索所有组件。

### 6.2 错误处理 🔴 强制

```typescript
// 方式一：在组件中用 try-catch
async function loadData() {
  loading.value = true
  try {
    const result = await getTaskList({ page: 1, size: 20 })
    tasks.value = result.items
  } catch (error) {
    // 错误提示已在 request.ts 拦截器中统一处理
    // 这里只需处理页面级的兜底逻辑
  } finally {
    loading.value = false  // ★ 不管成功失败都要关闭 loading
  }
}
```

## 7. Git 提交规范

### 7.1 Commit 消息格式 🔴 强制

```
格式：<type>(<scope>): <subject>

type 可选值：
  feat     — 新功能
  fix      — 修复 Bug
  style    — 样式调整（不影响逻辑）
  refactor — 重构（不新增功能，不修复bug）
  docs     — 文档更新
  chore    — 构建/依赖/杂务
  test     — 测试相关

scope：使用模块名（auto-qc / llm-qc / shared / layout）
  - 跨模块影响时不写 scope

subject：用中文简要描述修改内容

示例：
  feat(llm-qc): 新增质检任务批量导入功能
  fix(auto-qc): 修复规则编辑器未保存时数据丢失
  style(shared): 统一按钮 hover 动效
  refactor(layout): 侧边菜单改为读取路由配置动态渲染
  docs: 更新前端开发规范
```

### 7.2 分支策略 🟡 推荐

```
main         → 稳定版本，只通过 PR 合入
  └── dev    → 开发分支，日常合入
      ├── feat/llm-qc-batch-import   → 功能分支（完成后合入 dev）
      └── fix/rule-editor-save-bug   → 修复分支（完成后合入 dev）
```

## 8. Code Review Checklist

> PR 审查者必须逐项检查，全部通过后方可合入。

### 架构合规 🔴
- [ ] 文件放在正确的目录
- [ ] 没有跨模块直接 import 其他模块私有文件
- [ ] 通用代码放在了 `components/` / `utils/` 而非模块内部

### TypeScript 🔴
- [ ] 没有使用 `any`
- [ ] API 返回类型有明确定义
- [ ] 新数据结构有 interface 定义在 `types/` 中

### 组件质量 🔴
- [ ] `<style scoped>` 已添加
- [ ] 结构遵循 template → script → style 顺序
- [ ] 模板中无复杂逻辑表达式
- [ ] `v-for` 有 `:key`

### 样式质量 🔴
- [ ] 使用 CSS 变量（不硬编码颜色值）
- [ ] 没有 `!important`
- [ ] 布局使用 flex/grid（不使用 float）

### 通用 🟡
- [ ] 没有 `console.log` 残留
- [ ] 单文件不超过 300 行
- [ ] 有必要的注释（复杂逻辑处）

## 9. 禁止事项清单（速查）

```
🔴 绝对禁止（发现必须修改）：
  1. 使用 any 类型
  2. 模板中写复杂逻辑表达式
  3. 硬编码颜色值
  4. <style> 不加 scoped
  5. 组件中直接使用 axios
  6. v-for 不加 :key
  7. 直接操作 DOM（document.getElementById 等）
  8. console.log 残留在提交代码中

🟡 强烈不推荐（需在 PR 中说明理由）：
  1. 单个 .vue 文件超过 300 行
  2. Store 中直接操作 DOM
  3. 使用 !important
  4. 使用 float 布局
  5. 在 computed 中产生副作用（如修改数据、发请求）
```
