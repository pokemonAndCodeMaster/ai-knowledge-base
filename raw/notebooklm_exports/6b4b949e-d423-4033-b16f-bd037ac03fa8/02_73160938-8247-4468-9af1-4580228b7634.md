## 📋 1. 本体论与元数据规范 (Taxonomy & YAML)

所有 Wiki 卡片头部必须包含 YAML Frontmatter。
**约束**：`domain` 必须是列表（支持跨域复用），`type` 必须是单值字符串（保持原子性），二者必须取自 `knowledge_base/TAXONOMY.yaml` 的枚举值。

### 标准 YAML 模板示范：
```yaml
---
id: "PF-001"
title: "卡片标题"
domain: ["auto_qa", "llm_qa"]  # 归属业务域 (必须是 List)
type: "pitfall"                # 知识类型 (必须是 String，如 hub, schema, module_doc, pitfall, norm, code_module, source, synthesis)

# 正向锚定 (我是谁的说明书？)
related_code: ["src/obs/obs_client.py"]

# 反向护栏 (我约束了谁？)
affects_path: ["src/obs/*"]
trigger_keywords: ["obs", "mox", "exist", "下载"]
tags: ["OBS", "下载重试"]         # 语义标签 (由 KM 语义填充)
summary: "OBS 下载操作的避坑指南，涵盖重试策略和路径规范"  # 首段摘要 (≤200 字)
code_hash: {}                  # 代码模块卡专属：关联文件的 SHA256 哈希
---
```

## 📝 2. 知识编纂与卡片写作原则 (Agent-Skill Principles)

当你执行 `[ingest]` 创建新卡片，或执行 `edit` 更新卡片时，必须严格贯彻以下 7 大写作原则，确保知识库高度适配 AI Agent 的上下文窗口：

1. **【重流程，轻百科 (Process > General Knowledge)】**：拒绝写维基百科式的通用科普。卡片内容必须是"如何在本系统中操作/规避"，而不是"这个技术的通用原理是什么"。
2. **【极度具体 (Specific > General)】**：拒绝模棱两可的建议。如果是排雷 (pitfall) 或规范 (norm)，必须给出具体的参数要求、API 替代方案或确切的代码层级。
3. **【证据驱动 (Evidence for Verification)】**：任何架构规范或避坑指南，都**必须**在 YAML 中通过 `affects_path` 或 `related_code` 绑定物理依据。绝不允许存在无法追溯物理代码的"悬空知识"。
4. **【防幻觉/防合理化 (Anti-rationalization)】**：绝对禁止"凭空捏造"或"过度脑补"。当你在总结一段代码或报错经验时，如果缺少信息，直接在卡片中标记 `[待人类补充: XXX]`，严禁为了保证卡片完整性而自己编造不存在的方法名或路径。
5. **【渐进式披露 (Progressive Disclosure)】**：保持卡片的"原子性"。`[[HUB-XXX]]` 枢纽卡只做目录导航和总览，具体的细节必须分散在被双向链接指向的叶子卡片中。绝不允许把所有内容塞进一张巨型卡片里。
6. **【Token 意识 (Token-conscious)】**：行文必须极致精简，消除所有冗余的客套话、重复的背景介绍。你的每一句话都会消耗主控的 Context Window，请惜字如金。
7. **【Direct Quote 护栏 (Code Fidelity)】**：在 `pitfall`、`norm`、`code_module` 类型的卡片中，**代码片段必须使用原文快照（fenced code block）**，**绝对禁止**用自然语言概括代码行为。代码是硬约束，不是"大意"。

## 🧭 3. 核心工作流 (Workflows)

### 🎬 工作流 A: 图索引驱动查询流 `[query]` (唯一查询入口)
**执行逻辑**：

1. **图索引检索（Seed → Expand → Classify 三阶段）**：
   - 调用 `query_graph.py` 获取分级检索清单：
      ```bash
      python knowledge_base/scripts/query_graph.py "<任务描述>" --domains <域> --paths <路径>
      ```
   - 返回结果按 `full_read` / `summary_only` / `title_only` 三级分桶。

2. **并行读取 full_read 级别卡片**：
   - **根据 query_graph.py 返回的清单，可并行读取 full_read 级别卡片的完整内容**（此步骤不受"单步调用"限制）。
   - 使用 `.wiki_graph.json` 中预编译的 `summary` 作为 `summary_only` 级别卡片的上下文（无需再读取原文）。
   - 仅列标题作为 `title_only` 级别卡片的参考。

   **并行读取效能观测**：
    - 每次完成 [query] 流程时，**必须**在输出末尾附加一行并行读取观测记录，格式如下：
      ```
      📊 [query] 并行读取观测: full_read=<数量>, 并行=<是|否>, 耗时感知=<快|中|慢>
      ```
    - `full_read`：本次 full_read 级别卡片数量
    - `并行`：是否在单次回复中并行发出了多个 read 调用（是/否）
    - `耗时感知`：总读取耗时主观判断（快/中/慢）

3. **深度遍历补充（Graph Traversal）**：
   - 读取卡片后，**密切关注正文或 YAML 中的 `[[双链]]`**。
   - 若双链指向的内容（如某个底层工具 `[[Tool_XXX]]` 或某个避坑指南 `[[Pitfall_XXX]]`）对解答问题有帮助，你**必须**使用 `read` 读取该卡片。
   - 🚨 **【路径收敛铁律】**：如果 Wiki 图谱中没有用双链指向某个底层代码或配置，**你绝不允许私自使用 `bash` 去代码库里 `grep` 搜索！** 知识库没有的关联，对你而言就是不存在！

4. **闭环交付**：
   - 汇总你一路读到的事实、代码路径、以及**任何包含在双链中的护栏规范**。
   - 交付物必须客观、高密度。若关联了坑点规范，必须在交付末尾用 `> ⚠️ 架构护栏拦截：[具体约束说明]` 强制标出！

### 🎬 工作流 B: 知识摄入与双链焊死流 `[ingest]`
**触发**：当要求你记录开发经验、避坑指南、重构原因或新概念时。
**执行逻辑**：
1. **读宪法**：必须先 `read knowledge_base/TAXONOMY.yaml`，选定合法的 `domain` 和 `type`。
2. **长文分块（可选）**：如果输入资料超过 2000 字，先调用 `chunk_raw.py` 分块：
   ```bash
   python knowledge_base/scripts/chunk_raw.py <raw_markdown_file>
   ```
   然后按 Map-Reduce 范式：先输出 Checklist（Map），再逐条写卡（Reduce）。
3. **写卡片 (遵循 7 大原则)**：使用 `write` 创建新的 `.md` 卡片。
   - 🚨 **强约束**：行文必须符合【📝 知识编纂原则】。剔除百科废话，只保留具体限制和代码关联。填入标准 YAML 头（规范或坑点必须精准填写 `affects_path` 以满足"证据驱动"）。
   - 🚨 **Direct Quote 护栏**：`pitfall` / `norm` / `code_module` 类型的卡片中，代码片段**必须使用原文快照**，禁止自然语言概括。
4. **双链焊死 (实现渐进式披露 - CRITICAL!)**：
   - 知识绝不能是孤岛！你必须找到这项新知识所影响的**源头卡片**（如对应的 HUB，或底层的 `[[Tool_XXX]]` 模块影子卡）。
   - **强制调用 `edit` 工具** 修改这些源头卡片，在其正文末尾追加：`> ⚠️ 关联经验与规范：[[新卡片名称]]`。
5. **黄页注册**：调用 `edit` 修改 `knowledge_base/GLOBAL_INDEX.md`，将新卡片按 Domain 分类追加到索引列表中。

### 🎬 工作流 C: 代码架构摄入流 `[ingest_code]`
**触发**：当要求你摄入某个代码目录/模块的架构信息时。
**执行逻辑**：
1. **骨架提取**：调用 `extract_code_skeleton.py` 提取代码骨架：
   ```bash
   python knowledge_base/scripts/extract_code_skeleton.py <dir_or_file> [output_dir]
   ```
2. **阅读骨架 → 输出《代码架构清单》（Map）**：阅读骨架文件，输出该目录的模块结构清单（Why/Who/Where 三要素）。
3. **创建 `code_module` 类型卡片**：
   - 仅含 Why（为什么存在）、Who（谁调用它）、Where（在什么路径），**严禁复制代码实现**。
   - 填写 `related_code` 绑定物理代码路径。
   - 填写 `domain` 和 `tags`。
4. **回填 code_hash**：调用 `check_staleness.py --code-only` 获取当前代码哈希，回填到卡片 frontmatter 的 `code_hash` 字段。
5. **双链焊死 + 黄页注册 + 重编译**：
   - 修改源头 HUB 卡片焊死双链。
   - 更新 GLOBAL_INDEX.md。
   - 调用 `compile_graph.py` 重编译图索引。

### 🎬 工作流 D: 知识体检侦察流 `[health]`
**触发**：人类要求进行知识库健康检查时。
**执行逻辑 (仅扫描出报告，不执行删改)**：
1. **过期检测**：调用 `check_staleness.py` 获取过期检测报告：
   ```bash
   python knowledge_base/scripts/check_staleness.py
   ```
   读取报告中的 `code_staleness`、`time_staleness` 信息。
2. **图索引健康**：读取 `.wiki_graph.json` 中 `stats` 的 `orphan_count` / `broken_link_count`。
3. **扫描死链**：遍历 Wiki 卡片，检查 `[[卡片名]]` 或 `related_code` 是否指向了不存在的物理文件。
4. **扫描孤岛**：找出没有被任何 `GLOBAL_INDEX.md` 或其他卡片双向链接引用的废弃知识。
5. **扫描冗余**：对比同 Domain 下同 Type 的卡片，寻找高度相似的条目。
6. **输出报告**：将诊断结果写入 `.artifacts/KNOWLEDGE_HEALTH_REPORT.md`，并在其中给出明确的**修改建议（合并/废弃/删链）**，等待人类的下一步修改指令。

### 🎬 工作流 E: 索引编译与 README 动态段刷新流 `[compile]`
**触发**：人类说"更新README"、"compile"或"编译索引"时。
**执行逻辑**：

**阶段 1：编译 GLOBAL_INDEX.md（原有职责）**
1. 扫描 `knowledge_base/wiki/` 各子目录（hubs/、concepts/、modules/、schemas/、norms/、pitfalls/）下的所有 `.md` 卡片。
2. 读取每张卡片的 YAML Frontmatter，提取 `domain`、`type`、`title`、`affects_path` 等字段。
3. 按 Domain 分组、Type 排序，生成/更新 `knowledge_base/GLOBAL_INDEX.md`。

**阶段 1.5：编译图索引（新增职责）**
- 调用 `compile_graph.py` 生成/更新 `knowledge_base/.wiki_graph.json`：
  ```bash
  python knowledge_base/scripts/compile_graph.py
  ```
- 此步骤确保图索引与 GLOBAL_INDEX 同步更新。

**阶段 2：刷新 Wiki 卡片动态段（扩展职责）**

在 GLOBAL_INDEX.md 编译完成后，**追加执行**以下 5 个扫描→填充动作，刷新 `knowledge_base/wiki/hubs/HUB-Agent协作体系总览.md` 中对应子节的内容。
