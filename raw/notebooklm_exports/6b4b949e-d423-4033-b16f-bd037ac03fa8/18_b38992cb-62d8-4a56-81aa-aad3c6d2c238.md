## §3 关键实现契约（快照刷新四级契约）

> 本段从 [[验收前置条件-快照刷新四级实现契约]] 提取核心契约摘要。完整契约以原卡为准，本段为可实施摘要。

### 3.1 核心目标

实现统计快照表 `t_qc_daily_snapshot` 的定时刷新机制——每 30 分钟从 Delta 原始表聚合标注进度与验收结果，UPSERT 写入快照表，同时匹配 `t_personnel` 当前组别信息冗余写入 `group_name`。

### 3.2 数据流

```
Airflow DAG (每30min)
  └→ StatService.refresh_snapshot(stat_date_range)
       ├→ SnapshotRepository.fetch_annotation_raw(stat_date_range)
       │    └→ SELECT FROM delta.ods_t_label_screening_task_datalake JOIN delta.ods_t_label_sdobject_datalake_new
       │         按 (DATE(submit_time), task_screener, scene_name) 聚合
       ├→ SnapshotRepository.fetch_acceptance_raw(stat_date_range)
       │    └→ SELECT FROM delta.ods_t_label_screening_task_datalake
       │         WHERE task_status IN (67,68,69,70) 按 (DATE, screener, scene) 聚合验收结果
       ├→ PersonnelRepository.get_current_groups(employee_ids)
       │    └→ SELECT employee_id, current_group, project_name FROM t_personnel WHERE employee_id IN (...) AND leave_date IS NULL
       ├→ StatService._merge_with_personnel(raw_stats, personnel_map)
       │    └→ 将 task_screener(=employee_id) 映射到 employee_id + group_name
       └→ SnapshotRepository.upsert_many(merged_rows)
            └→ INSERT INTO t_qc_daily_snapshot ... ON CONFLICT (stat_date, scene_name, group_name, employee_id)
               DO UPDATE SET annotation_*=EXCLUDED.annotation_*, ... (不含执行字段)
```

### 3.3 四级契约摘要

| 层级 | 契约摘要 | 关键约束 |
|---|---|---|
| **DDL** | 4 张表双 schema 镜像（pnc_simulation + data_common_4），migration 幂等 | 禁 TRIGGER；updated_at 由应用层；`t_personnel.project_name` 单值；PG10+ 兼容 |
| **Repository** | SnapshotRepository（10 方法）+ PersonnelRepository（6 方法） | 全部 SQL 集中 Repository，Service 层禁拼 SQL；禁 ORM；参数化 `%s` 占位；upsert_many 用 `execute_values`，禁 `execute_query` 写；UPSERT 的 UPDATE SET 仅含统计列，禁触碰执行字段；显式带 `updated_at=now()`；SCD Type2 查询含 `WHERE leave_date IS NULL` |
| **Service** | StatService.refresh_snapshot(stat_date_range) → int；`_merge_with_personnel` 映射 task_screener → employee_id + group_name | 人员不存在时跳过并 warning；`current_group=''` 记录空串；scene_name 提取：e2e 项目 `SPLIT_PART(task_name, '_', 2)`，vpd 项目 `SPLIT_PART(task_name, '_', 3)`；`annotation_pending = total - submitted`（CHECK 约束保证非负） |
| **DAG** | `qc_snapshot_refresh` DAG，PythonOperator 调用 StatService.refresh_snapshot | `schedule_interval=30min`；`max_active_runs=1`；`dagrun_timeout=28min`；`catchup=False`；`retries=1`；`retry_delay=2min`；刷新最近 4 天；DAG 内禁业务逻辑；复用 `wrapper_failure_callback` |

- **bad_pass_rule**（revoke_and_pass.py:64-65）：`(good_bad验收总数 >= 总验收数 * 0.9 and 总脏数据通过率 > 0.7999) or (good_bad验收总数 < 总验收数 * 0.9 and 总通过率 > 0.9499)`
- **完成度前置**（revoke_and_pass.py:417-418）：`总验收数 >= 应抽数量 * 0.95 or 总验收数 >= 总提交数 * 0.95`

- **占比兜底**：当 good_bad 验收总数 < 总验收数 × 0.9（Good/Bad 样本占比不足 90%）时，用总通过率 > 0.9499 兜底

### 决策3：通过率阈值（旧版 good>0.9499, bad>0.7999）是否沿用？

- **① 背景**：人工验收完成后，根据通过率判定整组是否"通过"或"打回"。Good 类任务通过率 > 0.9499 且 Bad 类通过率 > 0.7999 则通过，否则打回。
  - 涉及组件：[[质检平台-通过打回规则与执行设计]] 的 PassRule
- **② 旧版源码事实**：`revoke_and_pass.py:62-65` 硬编码规则字符串：
  - good_pass_rule: `(good_bad验收总数 >= 总验收数 * 0.9 and 总good通过率 > 0.9499) or (good_bad验收总数 < 总验收数 * 0.9 and 总通过率 > 0.9499)`（严格 `>`）
  - bad_pass_rule: `(good_bad验收总数 >= 总验收数 * 0.9 and 总脏数据通过率 > 0.7999) or (good_bad验收总数 < 总验收数 * 0.9 and 总通过率 > 0.9499)`（严格 `>`）
  - 占比兜底：good_bad 验收总数 < 总验收数 × 0.9 时用总通过率 > 0.9499 兜底
- **③ PM 建议**：建议沿用 0.9499/0.7999 且保持严格 `>` 边界。理由：旧版已稳定运行；阈值有业务含义（95% 和 80% 的近似值），调整需业务侧确认。

- **② 旧版源码事实**：`revoke_and_pass.py:336-361` 的 `do_revoke` 调用 task_rollback 两次：
