## §3. Phase 详细计划

### Phase 1: t_llm_version_config 表设计 + DDL 落地

- **目标**：正向化 t_llm_version_config 表，补全完整 DDL + CHECK 约束 + 索引设计。
- **任务**：
  1. 编写迁移脚本 `scripts/sql/migrations/V20260702_02__create_t_llm_version_config.sql`
  2. 编写正式建表 SQL `scripts/sql/t_llm_version_config.sql`
  3. 编写测试镜像 SQL `scripts/sql/t_llm_version_config_test.sql`
  4. 确认 t_llm_task 表索引设计是否需调整（正向化确认）
- **产出**：3 个 SQL 文件 + DDL 落地验证
- **验收标准**：
  - DDL 遵循 NORM-GAUSSDB-DDL（DISTRIBUTE BY HASH；不支持 ADD COLUMN IF NOT EXISTS）
  - CHECK 约束齐全（channel 枚举 + version 非空 + config 非空）
  - 联合唯一约束 UNIQUE(version, channel) WHERE is_deleted=FALSE
  - 测试镜像 SQL 可在测试环境建表成功
- **设计依据**：[[大模型质检-t_llm_version_config表设计]] / [[大模型质检-t_llm_task表设计]]

### Phase 2: Repository 层重构

- **目标**：重构 TaskRepository + VersionConfigRepository，实现 SQL 集中封装 + 派生 status 机制。
- **任务**：
  1. 重构 `src/llm/task_repository.py` 的 TaskRepository（10 个方法）
  2. 重构 `src/llm/task_repository.py` 的 VersionConfigRepository（4 个方法）
  3. 实现 `_sync_task_status()` 派生机制
  4. 实现游标分页（fetch_task_list 补全 prev_cursor）
  5. 实现 UPSERT（upsert_version_config）
  6. 实现软删除规范（restore / permanent_delete）
- **产出**：Repository 代码 + 单元测试
- **验收标准**：
  - SQL 集中封装，Router 无 SQL
  - 参数化 SQL（%s 占位符），无 f-string
  - execute_query 禁写，写操作用 execute/execute_values
  - _sync_task_status 唯一写 status
  - 软删除规范遵守 NORM-SOFT-DELETE
- **设计依据**：[[大模型质检-Repository与数据库访问设计]]

### Phase 3: Router + API 契约重构

- **目标**：重构 Router 层，实现 14+4 端点 API 契约 + Pydantic Schema。
- **任务**：
  1. 重构 `src/api/routers/task.py`（14 端点）
  2. 重构 `src/api/routers/version.py`（4 端点）
  3. 重构 `src/api/schemas/task.py`（生产任务域 Schema）
  4. 重构 `src/api/schemas/version.py`（版本配置域 Schema）
  5. 新建 `src/api/schemas/common.py`（通用 Schema）
  6. 重构 `src/api/deps.py`（依赖注入）
  7. 统一路由前缀 /api/llm/
- **产出**：Router + Schema 代码 + 单元测试 + API 文档
- **验收标准**：
  - 14+4 端点全部实现
  - 路由前缀 /api/llm/tasks、/api/llm/versions
  - Pydantic 校验齐全
  - 统一响应格式 + 错误码体系（400/404/409/500）
  - 游标分页（任务）+ OFFSET 分页（版本）声明
  - 三层架构（无 AppService），Router 直接调 Repository
- **设计依据**：[[大模型质检-API契约与前端交互设计]] / [[大模型质检-领域模型层设计]] / [[大模型质检-后端分层与组件边界设计]]

### Phase 4: 前端推翻重写

- **目标**：前端推翻重来，TaskView 拆 5 组件，VersionView 拆 3 组件。
- **任务**：
  1. 重写 `src/frontend/src/views/TaskView.vue`（容器组件）
  2. 重写 `src/frontend/src/views/VersionView.vue`（容器组件）
  3. 新建 5 个 Task 子组件（TaskListView / TaskCreateDialog / TaskDetailPanel / ChannelStatusGrid / RecycleBinTab）
  4. 新建 3 个 Version 子组件（VersionListView / VersionFormDialog / VersionDetailPanel）
  5. 重写 `src/frontend/src/api/task.ts` / `src/frontend/src/api/version.ts`
  6. 重构 `src/frontend/src/router/index.ts`（路由 /llm/tasks、/llm/versions）
  7. 重构 `src/frontend/src/layouts/MainLayout.vue`
- **产出**：前端代码 + 组件测试 + e2e smoke
- **验收标准**：
  - 单组件 <300 行
  - 遵循前端开发规范（SFC 顺序 / style scoped / 禁 any / 禁 axios 直用 / 禁 v-for 无 key）
  - 6 通道 status 聚合展示（ChannelStatusGrid）
  - 游标分页双向交互（加载更多 + prev_cursor）
  - 回收站交互（restore + permanent_delete）
  - 创建弹窗（表单 Tab + 文件上传 Tab）
- **设计依据**：[[大模型质检-前端页面与状态设计]] / [[大模型质检-生产任务设计]] / [[大模型质检-版本配置设计]]

### Phase 5: 知识库同步刷新

- **目标**：知识库同步刷新，旧卡标注归档。

## §6. 风险与待决事项

### 6.1 风险清单

| # | 风险 | 影响 | 缓解策略 |
|---|------|------|---------|
| 1 | 前端推翻重写期间旧功能不可用 | Phase 4 期间大模型质检前端不可用 | 评估是否需要保留旧前端并行运行，或接受短暂不可用 |
| 2 | 游标分页补全 prev_cursor 可能影响现有前端 | 现有前端若依赖单向游标，补全 prev_cursor 后响应格式变化 | Phase 4 前端同步重写，响应格式变更在 Phase 3-4 同步 |
| 3 | UPSERT 联合键变更影响现有数据 | 若现有 t_llm_version_config 无联合唯一约束，Phase 1 DDL 落地需数据迁移 | Phase 1 前确认现有数据，必要时编写数据迁移脚本 |
| 4 | 派生 status 规则未完整定义 | [待人类补充] 派生规则不完整可能导致 _sync_task_status 实现偏差 | Phase 2 前确认完整派生规则 |
| 5 | 6 通道版本字段冻结约束的落地方式 | 应用层约束 vs 数据库约束 | Phase 2-3 确认（建议应用层约束，避免数据库层复杂触发器） |
| 6 | t_llm_task 与 t_channel_dedup_lock 关联未明确 | [待人类补充] 关联关系不明确可能影响 Repository 查询 | Phase 2 前确认关联关系 |

### 6.2 待决事项（[待人类补充]）

- [待人类补充] 派生 status 完整规则（mixed 状态、部分通道 pending 部分 completed 时的归属、kill 后通道 status 是否全部变更）。
- [待人类补充] restore 后 status 是否重置为 pending 还是保留原 status。
- [待人类补充] task_name 是否加唯一约束。
- [待人类补充] t_llm_task 与 t_channel_dedup_lock 的关联关系。
- [待人类补充] channel 枚举是否包含未来扩展通道。
- [待人类补充] processor 是否仅 prompt 通道必填。
- [待人类补充] UPSERT 联合键冲突时（已删除记录）是 INSERT 新记录还是恢复旧记录。
- [待人类补充] 测试镜像 SQL 的目标 schema。
